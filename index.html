Distributed File Storage System

02
Type
Full Stack
Status
In Progress
Medium
Go, SQL, Protobuf, Bash, gRPC, Docker, Kubernetes, MinIO, PostgreSQL, Prometheus, OpenTelemetry

A distributed object storage engine built in Golang with file chunking (4MB blocks), SHA-256 content-addressed deduplication, and a gRPC streaming service. This implements a consistent hash ring with virtual nodes and replication factor 3 across a MinIO cluster, reducing redundant storage by 40% in load-test benchmarks with others. Features PostgreSQL stored metadata versioning similar to Git in terms of permanent record like commits in Git, vector clock conflict detection, and CRDT merge strategies for concurrent disconnected writes. Deployed on a 3-node Kubernetes cluster with automatic leader election, regional request routing, and monitoring via Prometheus and OpenTelemetry.

Case file 03 · Machine Learning

d-RAG-on

My FullStack AI Chatbot built from scratch using a Retrieval-Augmented Generation (RAG) pipeline orchestrated using LangGraph.

03
Type
Machine Learning
Status
Advanced
Medium
Python, JavaScript, HTML, CSS, React, Vite, LangGraph, LangChain, Groq, Pinecone, Tavily, Docker

My FullStack AI Chatbot built from scratch using a Retrieval-Augmented Generation (RAG) pipeline orchestrated using LangGraph. It retrieves relevant documents from a Pinecone vector store. Then grades its relevance using Groq's llama-3.1-8b-instant model. If the retrieved context is not enough for it, it automatically falls back to live web search and scraping using Tavily. Users can also upload their own documents to extend the knowledge base of the system. The documents are also isolated per user using Pinecone namespaces. The document ingestion pipeline for the .txt and .pdf files are made using a text-splitter and Pinecone multilingual-e5-large inference embedding from Microsoft. The Backend is built using Python(FASTAPI) and the Frontend is made using React deployed on Vercel.

Case file 04 · LLM Evaluation

CodeJudge

An evaluation and training pipeline that tests whether a small language model (Qwen2-1.5B) can write a correct parse_amount() function, graded in a sandbox against a corpus of 30 million test cases.

04
Type
LLM Evaluation & Fine-tuning
Status
In Progress
Medium
Python, Qwen2-1.5B, LoRA, SFT, DPO, Hugging Face Transformers, Google Colab (T4)
Planned
GGUF / AWQ quantization, FastAPI, Prometheus, Docker, Kubernetes

CodeJudge tests whether a small language model (Qwen2-1.5B) can write a correct parse_amount() function for an ambiguous spec. Generated code runs in a sandbox, and a grader scores it against a corpus of 30 million test cases. Every number in the project comes from a script: a results ledger records the source and command behind each headline figure.

Supervised fine-tuning (done). I trained LoRA adapters on 117 solutions that passed every grader test, across 16 runs on a Colab T4: three training-set sizes by three seeds, a step-matched control, and an untrained baseline. Training worked, but written numbers make up 47.2% of the corpus and no run solved them (best 3.8%). Every working run scored 52.8–54.5%, matching the earlier models, so SFT did not improve the score. I documented that negative result instead of hiding it.

Preference training (in progress). DPO shows the model both a passing and a failing solution for the same prompt, aimed at the written-number failures. 468 preference pairs are built and checked, and the next step is a paired SFT vs SFT+DPO comparison across three seeds.

Next. An evaluation release gate that blocks regressions by category slice, then quantized serving behind a FastAPI gateway with metrics, Docker and Kubernetes. These are planned, not started.

Case file 05 · Machine Learning

JobFit

A job-posting ranker that benchmarks a probabilistic record-linkage baseline (Fellegi-Sunter) against classical ML and a fine-tuned transformer, then serves the best model on Triton Inference Server.

05
Type
Machine Learning
Status
Planned
Medium
Python, spaCy, NLTK, pandas, NumPy, scikit-learn, XGBoost, TensorFlow, Hugging Face (DistilBERT), PostgreSQL, ONNX, TensorRT, Triton Inference Server, gRPC, Docker, Weights & Biases, GitHub Actions

JobFit ranks job postings by relevance to a user’s stated preferences. It exists to answer one question: when is a cheap classical model the right production choice, and when is a transformer worth its latency and cost?

The comparison. A Fellegi-Sunter record-linkage baseline (a technique I have already used in a Chrome extension) is benchmarked against logistic regression, SVM, Naive Bayes, random forest, XGBoost, a TensorFlow MLP, and a fine-tuned DistilBERT. Every model runs on the same labeled posting–profile pairs, with splits grouped by profile and company to prevent leakage, stratified cross-validation, PR-AUC with bootstrap confidence intervals, and K-means / PCA clustering of the errors.

The serving path. The best transformer is exported to ONNX, optimized with TensorRT at FP32, FP16 and INT8, and served on Triton Inference Server over gRPC with dynamic batching. The trade-off between PR-AUC and P50/P95/P99 latency is measured, and every run is tracked in Weights & Biases.

Status. Planned: nothing is built yet, so there are no results to report. Every number will come from a script, and the limitations (synthetic user profiles, label noise, a small dataset, the hardware available) will be written down.
